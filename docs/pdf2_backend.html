PRICESIM · System Design Document

Backend Architecture

From raw Hyderabad listings to a serverless, LLM-powered price simulator: data pipeline, model training, artifact exports, TypeScript inference engine, API routes and deployment.

1. System overview

The system is a three-stage pipeline: an offline Python analysis layer produces trained models and JSON artifacts, a Next.js application layer re-implements those models in TypeScript for instant inference, and a serverless deployment (Vercel) serves it with an optional LLM for natural-language explanations.

Figure 1 — end-to-end data flow. Everything the app serves is an artifact of the Python pipeline; the web layer only reads artifacts and computes.

2.2 Feature engineering (scripts/prep_hyderabad.py)

  • Binaries: the 30 amenity columns are counts from the scrape; each is binarised to 0/1 (value ≥ 1 → 1).
  • Feature selection: 11 model features — area, bedrooms, resale, pool, gym, clubhouse, security, backup, car_parking, lift, vaastu.
  • Locality grouping: 241 raw locality strings are normalised (lowercase, non-alphanumeric stripped) and grouped into the 48 most frequent named areas plus Other (49 groups, drop-first coding ⇒ 48 dummies).
  • Coordinates: each locality maps to the mean (lat, long) of its rental listings; unmatched localities fall back to the city centre (24 rows). A DISPLAY dict restores proper names (“Banjara Hills”, “Hitech City”) after normalisation.
  • Sanity filters: 300 ≤ area ≤ 15,000 sq ft; ₹5 L ≤ price ≤ ₹50 Cr.

3. Model layer

3.1 Training protocol (scripts/train_export_hyderabad.py)

Data is split 80/20 (deterministic, random_state=42); all metrics below are reported on the 20% holdout. The target is modelled in INR millions (price_scale = 1e6) for numerical stability; the app multiplies back to rupees at display time.

ModelMethodHoldout R²RMSE
Area onlyOLS, 1 feature0.693₹43.99 L
Multiple (11 features)OLS0.709₹42.86 L
Multiple + localityOLS + 48 dummy columns0.775₹37.68 L
Neural netMLP 32→16, ReLU, Adam, early stopping0.714₹42.46 L

The full model is fitted by Ordinary Least Squares on the design matrix X = [1, features, dummies]:

β = (XᵀX)⁻¹ Xᵀy

Locality coefficients are interpretable premia: Banjara Hills +₹89.9 L, Jubilee Hills +₹84.1 L, Madhapur +₹41.7 L … Attapur −₹24.1 L, Tellapur −₹21.8 L — relative to the reference locality, controlling for all features.

4.2 Inference engine (web/lib/predict.ts)

The TypeScript engine reproduces the Python algebra exactly:

  • predictLinear — mean-centred decomposition: prediction = (intercept + Σ coef·mean over all columns) + Σ coef·(x − mean) + locality dummy sum. The mean-centring constant is rebuilt from the exported arrays so the two sides cannot drift apart.
  • predictMlp — exact MLP forward pass: feature standardisation, 32→16 ReLU hidden layers, identity output; sklearn matrices are stored (n_in × n_out) and transposed on the fly.
  • nearestHouses — in-memory k-NN over the standardised 11 features against all 2,518 bundled records (O(n) per query, ~2 ms).

Sample response of /api/predict (1,500 sq ft, 3 BHK, amenities, Banjara Hills):

4.3 AI assistant flow

  1. Regex parser extracts area (sq ft / sq m / sq yd), BHK, resale/new, amenity keywords, and the locality by longest match against city_map keys.
  2. A feature payload is built and run through the same predictLinear/predictMlp.
  3. An OpenAI-compatible call is made to OpenCode Go (https://opencode.ai/zen/go/v1/chat/completions, model glm-5.3-flash) with a system prompt that hands the model the computed numbers; the response is the final narrative.
  4. If no API key is set (or the call fails), a template engine writes the same style of answer from the model output — the app never breaks.
Engineering details that matter: OpenCode Go requires a non-generic User-Agent (Cloudflare 403 otherwise) and a stable x-opencode-session header; the key lives only in server env vars (never git); the chosen model returns direct content (reasoning models can exhaust the token budget on inner monologue).

4.4 Tax card

All-in cost = price × (1 + (stamp_duty% + registration%)/100), with rates (4% + 1%) configurable in web/lib/config.ts and labelled as approximate Telangana rates.

5. Serverless deployment & operations

5.1 Vercel

  • Project prutxvis-projects/real-estate-price-simulator, alias https://real-estate-price-simulator.vercel.app, deployment protection off.
  • Every model artifact is bundled into the serverless functions at build time — no runtime filesystem reads (Node lambdas cannot read public/). This constraint drove the k-NN rewrite to an in-memory import.
  • Env vars (API key, base URL, model) are set per environment (production/preview/development).
  • Static content (houses.json, figures) is served by the Vercel CDN.
# deploy
cd web
vercel --prod --yes
# local
npm run build && PORT=3100 npm start

5.2 CI (.github/workflows/ci.yml)

  • data-pipeline job: installs the analysis stack, reruns prep → train → figures on every push/PR, so the committed artifacts are always reproducible.
  • web-build job: npm ci && npm run build in web/.
